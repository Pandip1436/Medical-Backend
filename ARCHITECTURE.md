### Neon-specific design notes
- The Prisma datasource uses a split connection model: runtime traffic on the **pooled** `DATABASE_URL`, while migrations use a **direct** `DIRECT_URL` (Neon's transaction-mode pooler doesn't hold the session-level advisory locks that `prisma migrate` needs).
- GRN create/edit transactions run with extended timeouts (`maxWait: 15s, timeout: 60s`) because multi-line writes over the pooler routinely exceed Prisma's default 5s and surface as `P2028`.
- `JwtStrategy` caches the per-user validation lookup in memory for **30s** to avoid exhausting the Neon connection pool when the frontend fans out parallel calls on page load.

### Bootstrap configuration (`main.ts`)
- **No global route prefix is set in `main.ts`.** Each controller declares its own prefix (almost all are `api/v1/<resource>`). The root `AppController` serves `GET /`.
- CORS is open (`origin: true, credentials: true`).
- Global `ValidationPipe` with `whitelist: true`, `transform: true`, **`forbidNonWhitelisted: false`** (unknown fields are silently stripped, not rejected).
- `rawBody` is preserved on the express `json()` middleware (50mb limit) so webhook controllers can verify **HMAC-SHA256 signatures** against exact provider bytes.
- A global `AuditLogInterceptor` is registered as an `APP_INTERCEPTOR`.

### Multi-Tenancy / Branch (Location) Isolation
The system is **multi-branch** (each physical pharmacy/location is a `Branch`). Isolation is enforced as follows:

1. **The allowed set.** A `User` has a home/default `branchId` plus a `UserBranch[]` join table listing every branch they may access. A `SUPER_ADMIN` has **no** `UserBranch` rows and may access **every** branch.
2. **Active-branch resolution (the key mechanism).** The frontend injects the desired branch via the `?branchId=` query param on each request. `JwtStrategy.resolveBranch()` validates it:
   - `SUPER_ADMIN` → may view any requested branch; no request = `null` = **all branches**.
   - Regular user → the requested branch is honored **only if it's in their allowed set**; a forged/out-of-set id silently falls back to the home branch.
3. **Service-level scoping.** The resolved `branchId` is passed into services, which:
   - **Filter list queries** by `branchId` when present (`where.branchId = branchId`).
   - **Guard single-record reads/writes** with the pattern
     `if (branchId && row.branchId && row.branchId !== branchId) throw NotFoundException` — cross-branch access returns 404 (not 403), avoiding existence disclosure.
4. **Global rows.** Many entities allow `branchId = null` (e.g. shared catalog/categories). A `null` branch row is visible across branches by design (the guard short-circuits when `row.branchId` is null).
5. **Approval branch isolation.** A branch-bound admin can only approve/reject `ApprovalRequest`s from their own branch; super-admins (no branchId) can review anything.

> **Note:** Isolation is **applied per-service**, not via a single global tenant guard or Prisma middleware. Correctness depends on each service threading and checking `branchId`. This is consistently done in the audited services but is a convention, not a structurally enforced invariant.

## 2. Core Features & Business Logic (Currently Implemented)

### 2.1 Inbound Procurement (PO → GRN → Batch → Expiry)

**Workflow:**
1. **Purchase Order (`PurchaseOrder`)** — optional starting point. Lines carry `requiredQty`, `expectedRate`, and a running `receivedQty`. Status flows `DRAFT → SENT → ACKNOWLEDGED → PARTIALLY_RECEIVED → FULLY_RECEIVED → CLOSED`.
2. **Goods Received Note (`GRN`, surfaced as "Purchase Entry / PE")** — the inbound stock event. On `create()` (one Prisma transaction):
   - Issues an atomic, FY-aware GRN number via `DocumentNumberingService`.
   - If linked to a PO, **validates against over-receipt** — no line may exceed the PO's remaining qty across all sibling GRNs.
   - For each item, **creates a `Batch`** carrying `batchNumber`, `mfgDate`, `expiryDate`, `quantity (= receivedQty + freeQty)`, `mrp`, `purchaseRate`, `supplierId`, and a back-link `grnItemId`.
   - **Increments `Product.totalStock`** and refreshes the product's `purchaseRate`/`mrp` to the latest received values.
   - **Books the payable:** supplier `currentOutstanding` rises by the full `supplierInvoiceAmount`; any amount paid at receive-time is recorded as a `SupplierPayment` credit, so net outstanding rises only by the unpaid portion (double-entry).
   - Derives `paymentStatus` (`UNPAID`/`PARTIAL`/`PAID`) from paid-vs-invoice.
   - Recomputes the linked PO's `receivedQty` and status.
3. **Replacement GRNs** (`isReplacement: true`) add stock back **without** creating a payable — used to receive supplier replacements for returned goods.
4. **Expiry tracking** is batch-native: every `Batch` has a non-null `expiryDate`. Expiry is consumed downstream by:
   - The **sales path**, which hard-blocks dispensing expired batches.
   - The **notifications scheduler** + `GET /reports/inventory/expiry` (expired and near-expiry within 90 days).
5. **GRN edit (`editGrn`)** is allowed **only while the GRN's batches are untouched** — it counts references in `InvoiceItem`, `CreditNoteItem`, `PurchaseReturnItem`, and `StockAdjustmentLog`; if any batch has moved, the edit is refused and the user is told to use a Purchase Return / Stock Adjustment. When permitted, it reverses old stock + payables, reapplies the new items, recomputes the PO, and writes a before/after `GrnEditLog`.

**Purchase Returns / Debit Notes (`PurchaseReturn`)** — returns to suppliers:
- Settlement modes: `REFUND`, `REPLACEMENT`, `ADJUST`.
- **Short-delivery** returns (reason matches `/short.*delivery|short.*supply/`) skip stock deduction (goods never arrived) and are auto-flagged `stockReversedAt` so the admin sweep can never re-add phantom stock.
- All other reasons deduct physical stock from the batch.
- `ADJUST` immediately reduces supplier `currentOutstanding` (with a guard refusing to push it negative) and marks the note `SETTLED`.
- `REPLACEMENT` is settled later via `link-replacement` once a replacement GRN is confirmed (validates same supplier + `isReplacement` flag).

### 2.2 Outbound Sales (Invoicing, Inventory Deduction, Pricing Guardrails)

**Invoice creation (`BillingService.create`, one transaction):**
- Supports `INVOICE` and `QUOTATION` types; `RETAIL`/`WHOLESALE` billing; payment modes `CASH/CARD/UPI/CREDIT/SPLIT`.
- All money/percent fields are rounded to 2 dp (`r2()`) before persistence to keep Tally/GSTR exports clean.

**Inventory deduction — manual batch selection (NOT automatic FEFO):**
- ⚠️ **The backend does *not* perform automatic FEFO allocation.** Each invoice line arrives with an **explicit `batchId`** chosen by the client; `deductStockForItem()` validates and decrements *that specific batch*. The frontend is expected to present batches in FEFO order, but the server honors whatever batch id it is given.
- Per line, `deductStockForItem()`:
  - Loads the batch (404 if missing).
  - **Blocks expired stock** (`expiryDate` end-of-day < now → 400) — pharmacies can't legally dispense expired drugs.
  - **Blocks insufficient stock** (`batch.quantity < qty` → 400).
  - Decrements `Batch.quantity` and `Product.totalStock`.
  - Fires a **LOW_STOCK** notification when stock crosses `minStock`/zero, with layered suppression (respects prior read/resolve/snooze, 24h dedupe) so it doesn't re-fire on every sale.
- The single FEFO-relevant server guard is `assertUniqueName` on products — it rejects duplicate product names per branch precisely because "two products with identical names break FEFO selection."

**Pricing guardrails:**
- **Pricing sanity** is enforced server-side in `ProductsService.assertPricingSane()` on create/update: **selling price ≤ MRP** (MRP is the legal ceiling under the Drugs Price Control Order), **purchase rate ≤ selling price** (no selling below cost), and **purchase / wholesale rate ≤ MRP**. Purchase and wholesale rate are optional, so their checks only apply when a positive value is provided. Enforced in the product master, not at billing time — line `rate` on an invoice is otherwise trusted from the client. The same rules mirror the frontend Zod schema (`productFormSchema.ts`).
- **Schedule H/H1/X prescription guardrail** (`assertPrescriptionForScheduledItems`): scheduled drugs cannot be sold to a walk-in (no customer) and require an **active, non-expired `Prescription`** on file. **Wholesale** customers (licensed distributors) are exempt.
- **Credit-limit / pending-credit guardrail:** a new `CREDIT` sale is blocked when the customer already has ≥ `MAX_PENDING_CREDIT` (default 3) unsettled credit invoices. For a `PHARMACIST` this auto-routes into the **approval workflow** (saved as DRAFT + `CREDIT_BILL` request); for an `ADMIN` it hard-blocks.
- **Customer credit auto-apply:** if a customer carries a negative outstanding (prior credit balance), a new credit/split sale auto-applies that credit, bumps `amountPaid`, and records a `CREDIT_APPLIED` `Payment` row for auditability.

**Draft & edit lifecycle:**
- **Drafts** (`status: DRAFT`) skip *all* side effects — no stock, ledger, or notifications. They become real only at `finalize` (which runs the full prescription + stock + ledger + payment-due path) or are re-saved via `save-draft`.
- **Edit unpaid/partial/paid invoice** (`editUnpaidInvoice`): in one transaction, reverses original stock + customer ledger, re-validates and re-applies the new items, recomputes status from preserved `amountPaid`, and writes an `InvoiceEditAudit` before/after row. Blocked for `CANCELLED`/`RETURNED` invoices and any invoice that already has a credit note.
- **Quotation → Invoice** (`convertToInvoice`): quotations reserve no stock; conversion runs the full validate-and-deduct path.
- **Payment collection** (`collectPayment`): requires a reference number for all non-cash modes, rejects overpayment, updates customer outstanding, issues a `RCPT` receipt, and syncs the Payment Due reminder.

**Sales Returns → Credit Notes (`CreditNote`) — two-gate approval:**
- **Gate 1 (authorization):** a non-super-admin's return is filed as a `SALES_RETURN` `ApprovalRequest`; only a **Super Admin** can approve it, which then creates the real `PENDING_REVIEW` credit note. A Super Admin filing directly skips Gate 1.
- **Gate 2 (physical inspection):** the CN sits in `PENDING_REVIEW` with **no side effects** (stock not restored, outstanding untouched, invoice not flipped) until a reviewer `approve()`s — guarding against bad goods going back on shelves before inspection.
- On approve: restores stock; for `CREDIT` settlement, decrements customer outstanding and **cascades the credit** (source invoice first, then other open invoices oldest-first FIFO, remainder kept as customer-level credit); for `REFUND`, writes a `Refund` row (cash-book/ledger visible, `@unique` on `creditNoteId` prevents double-pay); `REPLACEMENT` stays unsettled. When cumulative *approved* returns ≥ invoice total, the invoice flips to `RETURNED`.
- Return quantities are capped at `sold − already-returned`, counting both `APPROVED` and `PENDING_REVIEW` CNs so back-to-back submissions can't double-count.

**Exports & integrations from sales:** Tally XML voucher export, CSV export, WhatsApp invoice delivery (event-driven), Razorpay payment-QR generation + webhook reconciliation, and a public customer pay-page.

### 2.3 Role-Based Access Control (RBAC)

**Roles** (`Role` enum, highest privilege first per `ROLE_PRECEDENCE`):
| Role | Intent |
|---|---|
| `SUPER_ADMIN` | Global owner — bypasses every role gate; all-branch access; sole approver of sales returns |
| `ADMIN` | Branch administrator — full operational + admin power within their branch |
| `PHARMACIST` | Front-desk dispensing, billing, customers, returns (often via approval) |
| `INVENTORY_MANAGER` | Products, batches, suppliers, GRNs, purchase orders/returns |
| `ACCOUNTANT` | Financial reports, payments, expenses, ledgers, GST |
| `SALESPERSON` | CRM (leads/contacts/companies), own stats; mostly read-only on operations |

**Enforcement mechanism:**
- A `User` carries a `roles: Role[]` set (the singular `role` is a derived "primary" for display/behaviour). **All permission checks read the full set.**
- The JWT (`JwtStrategy`) attaches `{ userId, email, role, roles[], branchId, branchIds[], isSuperAdmin }` to `req.user`.
- **`JwtAuthGuard`** (passport-jwt) authenticates; **`RolesGuard`** authorizes by reading the `@Roles(...)` metadata. Logic: if no `@Roles` → allow; if user has `SUPER_ADMIN` → allow; else the user's roles must intersect the required set.
- Almost every controller applies `@UseGuards(JwtAuthGuard, RolesGuard)` at the **class level**, with `@Roles(...)` per handler. A few set class-level `@Roles` (e.g. `BackupController` → ADMIN-only; `RemindersController` → ADMIN/PHARMACIST).
- **Approval workflows** are the privilege-escalation safety valve: privileged actions attempted by lower roles (credit bills over the pending limit, sales returns, large stock adjustments, purchase returns) are converted into `ApprovalRequest`s that an admin/super-admin must approve. The executor **re-validates** at approval time (stock, prescription, outstanding) because state may have changed since the request.

**Public / unauthenticated endpoints** (no guard — by design): the customer pay-page, Razorpay webhook, Meta WhatsApp webhook (verify + receive), and the IndiaMART lead webhook. Webhook security relies on **HMAC signature verification** (Razorpay/Meta) or **URL-token secrecy** (IndiaMART), plus `WebhookEvent` idempotency.

## 3. Database Schema Summary

The schema (`prisma/schema.prisma`) is large (~50 models). Core operational entities and their relationships:

### Identity, tenancy & access
- **`Branch`** — the tenant/location. Nearly every operational entity has an optional `branchId` FK back to it.
- **`User`** — staff. `roles[]` drives RBAC; `branchId` is home branch; `branchAccess` (**`UserBranch`** join) is the allowed-branch set. Author of invoices, audits, approvals, activities, backups.
- **`UserBranch`** — many-to-many user↔branch allow-list (empty for super-admins).

### Catalog & stock
- **`Product`** — drug master (pricing: `mrp`/`purchaseRate`/`sellingRate`/`wholesaleRate`, `gstRate`, `hsnCode`, `schedule`, stock thresholds, `totalStock` rollup). Belongs to a `Category`, optional `preferredSupplier`, self-relation `alternatives`.
- **`Batch`** — a received lot of a product: `batchNumber`, `expiryDate`, `quantity`, `mrp`, `purchaseRate`, `supplierId`, and `grnItemId` back-link. **The unit of inventory** — sales/returns/adjustments all move `Batch.quantity`.
- **`Category`**, **`StockAdjustmentLog`** (audit of manual stock changes).

### Procurement
- **`Supplier`** — vendor; `currentOutstanding` = money we owe.
- **`PurchaseOrder` / `PurchaseOrderItem`** — orders to suppliers.
- **`GRN` / `GRNItem`** — goods receipts; spawn `Batch`es; raise supplier payable. **`GrnEditLog`** audits edits.
- **`SupplierPayment`** — money paid to suppliers (FIFO-allocated across open GRNs when no `grnId`).
- **`PurchaseReturn` / `PurchaseReturnItem`** — debit notes to suppliers.

### Sales & receivables
- **`Invoice` / `InvoiceItem`** — the sale (also used for `QUOTATION` type). Links `Customer`, `Doctor`, `salesperson (User)`, optional CRM `Lead`. Snapshots `batchId`/`batchNumber`/`expiryDate` per line. **`InvoiceEditAudit`** records edits.
- **`Customer`** — `currentOutstanding` = money owed to us; `creditLimit`; type `RETAIL/WHOLESALE/DOCTOR`.
- **`Payment`** — money received from customers (invoice-scoped or customer-level lump).
- **`CreditNote` / `CreditNoteItem`** — sales returns (two-gate lifecycle). **`Refund`** — the cash payout for a REFUND-settled CN (1:1 with CN).
- **`Quotation` / `QuotationItem`** — standalone quotation system (coexists with `Invoice.type = QUOTATION`).
- **`Prescription`** — gates Schedule H/H1/X dispensing.

### CRM (sales pipeline)
- **`Company`**, **`Contact`** (can be promoted into a `Customer`), **`Lead`** (anchored to a Contact; pipeline/stage/score; IndiaMART fields), **`LeadActivity`**.
- Per-party interaction logs: **`SupplierActivity`**, **`CustomerActivity`**, **`LeadActivity`**, plus the monthly **`CustomerReminder` / `ReminderContact`** follow-up system.

### Platform / cross-cutting
- **`ApprovalRequest`** — generic approval queue (`NEW_CUSTOMER`, `CREDIT_BILL`, `SALES_RETURN`, `PURCHASE_RETURN`, `INVENTORY_ADJUSTMENT`).
- **`Notification`** — in-app alerts (`LOW_STOCK`/`EXPIRY`/`PAYMENT_DUE`/`SYSTEM`/`APPROVAL`) with snooze/resolve and escalation state.
- **`AuditLog`** — global write audit trail.
- **Numbering:** **`DocumentSequence`** (atomic per-`(docType, branch, FY)` counter) + **`NumberingConfig`** (per-branch format templates).
- **Integrations:** `IntegrationCredential`, `IntegrationSyncJob` (IndiaMART); `PaymentLink` (Razorpay QR); `WhatsAppMessage` (outbound + retry); `WebhookEvent` (idempotency/audit for Razorpay & Meta).
- **`Expense`**, **`SharedFile`** (expiring public PDF links), **`Backup`** (R2 snapshots), **`GlobalSetting`**.
- Deprecated-but-retained: **`DiscountRule`** (no longer wired to billing), `Branch.invoicePrefix` (superseded by `NumberingConfig`).

## 5. Missing Pieces & Critical Gaps

The following are observations from the source scan — a mix of true gaps, risk areas, and design choices worth knowing about. Ordered roughly by impact.

### 5.1 Concurrency: stock deduction is read-then-write (oversell risk)
`BillingService.deductStockForItem()` reads the batch, then writes an **absolute** value: `data: { quantity: batch.quantity - item.quantity }`. Under PostgreSQL's default `READ COMMITTED` isolation, two concurrent sales of the **same batch** can both read `quantity = 5`, both pass the availability check, and both write — a classic lost update that **oversells** the batch. The reverse paths correctly use atomic `{ decrement }`/`{ increment }`. For a single-counter pharmacy the practical risk is low, but it is a genuine correctness gap (no atomic conditional decrement, no row lock, no optimistic version column). The same read-then-write shape appears in the approval-time `CREDIT_BILL` re-validation.

### 5.2 "Automatic FEFO" is not implemented server-side
The brief's "automatic FEFO inventory deduction" does **not** exist in the backend. Deduction always targets the **client-supplied `batchId`** (manual selection); the server only blocks expired/short batches. If FEFO is a hard requirement, the backend currently cannot guarantee it — a client could submit any in-stock batch. (FEFO ordering is presumably a frontend concern.)

### 5.3 Migration/maintenance endpoints are live `GET`s with side effects
Six `GET /api/v1/grn/admin/*` routes (and the `reverse-short-delivery-stock` fix) **mutate data** — backfills and stock reversals — yet are exposed as idempotent-looking `GET`s. Issues:
- `GET` with write side effects is non-RESTful and can be triggered by prefetchers/crawlers/link-scanners.
- Several of these (`reverseShortDeliveryStockDeduction`, `backfillSupplierOutstanding`, `backfillGrnOrderedQty`, `backfillPoReceivedQty`, `backfillBatchGrnItemId`) run their loops **outside a `$transaction`** — a mid-run failure leaves partially-applied state. Idempotency is only partial (the stock-reversal one guards via `stockReversedAt`; the pure backfills are re-runnable but not atomic).
- These are one-time migrations that remain in the production surface area indefinitely.

### 5.4 `latest-wins` purchase rate / MRP on GRN
`applyGrnItems` updates `Product.purchaseRate` and `Product.mrp` to the values of whatever GRN line is being processed, with **no date comparison**. Entering an older-dated GRN after a newer one will overwrite the product master with stale pricing (it's "latest entered," not "latest dated").

### 5.5 Untyped / mass-assignment update paths
`BillingService.update()` (`PATCH /billing/:id`) accepts `data: any` and passes it straight to `prisma.invoice.update`. With no DTO, the global `ValidationPipe` whitelist has nothing to strip against, so this is an over-posting surface (a client could patch fields beyond the intended cancel use-case). `forbidNonWhitelisted: false` globally means unexpected fields are silently dropped elsewhere rather than rejected.

### 5.6 Non-atomic receipt numbers in one path
Most documents use the atomic FY-aware `DocumentNumberingService`. However, the **credit auto-apply** payment writes receipts as `RCT-CR-${Date.now()}-${random}` (in both `create` and `finalizeDraft`). This bypasses the sequence service — non-sequential, and a (small) collision/duplicate-display risk under bursty concurrency.

### 5.7 Auth cache staleness window
`JwtStrategy` caches user validity (active flag, roles, branches) for **30s**. A deactivated user, a role change, or a branch-access revocation can take up to 30s to take effect. This is an explicitly documented tradeoff for Neon pool protection, but it means revocation is **not immediate**.

### 5.8 Edit-invoice stock restore assumes original batch still exists
`editUnpaidInvoice` restores stock by `increment`-ing the **original** `batchId` from the old line. If that batch was since deleted (e.g. a GRN edit/reversal removed it), the `prisma.batch.update` would throw, failing the edit — an unhandled edge case rather than a graceful fallback.

### 5.9 Overlapping/duplicate quotation models
Quotations exist **twice**: as a standalone `Quotation`/`QuotationItem` model (with its own controller) and as `Invoice` rows with `type = QUOTATION` (created/converted by `BillingService`). Two sources of truth for "a quotation" invite divergence and reporting confusion.

### 5.10 No rate limiting / throttling
There is no `@nestjs/throttler` (or equivalent) in the dependency set or modules. The public endpoints (login, webhooks, customer pay-page, IndiaMART token webhook) are unthrottled — brute-force/abuse mitigation relies entirely on signature/token checks and downstream idempotency.

### 5.11 Tax handling is client-trusted
CGST/SGST/IGST amounts and `taxableAmount` are taken from the client payload and only rounded (`r2`) server-side. There is no server-side tax recomputation or interstate (IGST vs CGST/SGST) determination from GSTINs — the totals are trusted as submitted.

### 5.12 Minor / housekeeping
- **`mfgDate` no longer captured** at the GRN form level — it defaults to "today" when missing, so batch manufacturing dates are approximate for new receipts.
- **Deprecated-but-present:** `DiscountRule` model (unwired from billing), `Branch.invoicePrefix` (superseded by `NumberingConfig`) — dead schema kept intentionally but worth eventual cleanup.
- **Audit coverage:** a global `AuditLogInterceptor` exists, but explicit before/after audit trails are only implemented for invoices (`InvoiceEditAudit`), GRNs (`GrnEditLog`), and stock adjustments (`StockAdjustmentLog`); other mutations rely on the generic interceptor.
- **No `TODO`/`FIXME`/`HACK` markers** were found in the source — the gaps above are inferred from logic, not left as code comments.
- **Test coverage is thin** — a handful of `.spec.ts` files exist (auth, billing, products, GRN, suppliers, purchase-orders, customers, reports) but most modules are untested.
